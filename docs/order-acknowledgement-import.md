# 卸業者の受注確定CSV取り込み(発注側から見た設計)

卸業者が発注に対して引き当てを行った結果(確定数量・欠品・**納入単価**)をCSVで受け取り、
`purchase_orders` / `purchase_order_lines`に反映する仕組みについて、**現状の欠けと未確定事項**をまとめる。

> **未実装。** 反映先の列もドメインのフィールドも存在せず、取り込み処理も未着手
> (取り込み側リポジトリ clinic-inventory-csv-functions の
> `docs/catalog-import-pipeline.md`で「受注確定CSV・売上明細CSV | 未着手」)。
> このドキュメントは実装前に論点を固定するためのもので、確定した設計ではない。

- 位置づけ: `docs/architecture/domain-rules.md`(clinic-inventory側)の3種類のCSVのうち「受注確定CSV」
- 姉妹ドキュメント: 商品マスタCSVは[catalog-import-backend.md](catalog-import-backend.md)
- S3バケット・IAMの実設定は[s3-storage.md](s3-storage.md)

## 1. なぜ必要か — 発注時の単価と納入単価は一致しない

医薬品卸の業務では、**発注時点の単価と、卸が引き当てて実際に納入する時点の単価が変わることがある**。
納入単価を受け取れないと、次の2つが成立しない。

- 請求突合ができない。卸からの請求額と自システムの発注金額が合わず、差分の原因を追えない
- クリニック商品の仕入単価を実勢に合わせられない。医院別単価は登録時点の値をコピーする設計のため、
  受注結果を反映する経路が無いと古い単価が残り続ける
  (`backend/internal/application/productcatalog/register_clinic_product.go`(clinic-inventory側)の
  「単価は後日、卸から届く受注結果の単価で更新する運用」というコメントは、この経路を前提にしている)

単価のスナップショットは現状3段階まであり、4段目が欠けている。

| 段階 | 保存先 | 実装 |
|---|---|---|
| 卸のカタログ単価 | `distributor_products.unit_price` / `distributor_product_facility_prices.unit_price` | あり |
| 自院マスタの仕入単価 | `clinic_products.unit_price` | あり |
| 発注時点の単価 | `purchase_order_lines.unit_price` | あり |
| **納入時点の単価** | — | **無い** |

## 2. 「確定」が2つあり、用語が衝突している

| 誰の確定か | 意味 | 現状 |
|---|---|---|
| クリニックの発注確定 | 下書きを締めて卸に送る | `purchase_orders.status = 'confirmed'`、`confirmed_at` |
| 卸の受注確定 | 卸が引き当てを終え、数量と単価が決まった | 表現する手段が無い |

`OrderStatus`は`draft` / `confirmed`の2値のみ
(`backend/internal/domain/procurement/purchase_order.go`(clinic-inventory側))。
この`confirmed`はクリニック側の操作(`Confirm()`)を指すため、
**「卸に送ったあと相手がどうしたか」を表す状態が存在しない**。
実装する際は、既存の`confirmed`の意味を変えずに卸側の状態を別途足す必要がある(意味を変えると既存の発注データの解釈が変わる)。

## 4. 未確定: 分納・複数回確定があるか

受け皿の形は、1発注明細に対して確定が何回来るかで決まる。

| ケース | 必要な形 |
|---|---|
| 確定1回・納品1回 | `purchase_order_lines`への列追加で足りる |
| 確定1回・納品が複数回に割れる | 子テーブルが必要。粒度は「納品」 |
| 確定自体が複数回(「残り4個は取り寄せて後日確定」) | 子テーブルが必要。粒度は「確定」 |

**分からない場合は「確定単位の子テーブル」を選ぶ。** 確定が1回しか来なくても子が1行になるだけで無駄にならず、
逆に列追加で作ってしまうと、複数回が後から判明した時点でマイグレーションとコードの書き換えが発生するため。

### 設計案(暫定)

```
purchase_order_lines(不変・発注時のスナップショット)
  quantity, unit_price

  └─ purchase_order_line_deliveries(受注確定CSVが1行ずつ積む)
       confirmed_quantity    確定数量
       delivered_unit_price  納入単価(回ごとに変わりうる)
       acknowledged_at       卸の確定日時
       ingestion_run_id      どのCSV取り込みで入ったか
```

- 発注明細は書き換えないため、「確定後は明細を変更できない」という既存の不変条件を保てる
- 欠品数量は`発注数量 - Σ確定数量`で導出する。列として持つと、分納の途中経過で発注数量との辻褄が合わなくなる
- 明細ごとの状態(完納 / 一部 / 欠品確定)も導出できるため、ヘッダに状態を持たせなくてよい

### 代償: 冪等性を自前で担保する必要がある

子テーブルは行を積む形のため、**同じCSVが2回届くと二重計上する**(列を上書きする形なら自動的に冪等だった)。
商品マスタ側と同じく、`s3_key + etag`で取り込み済みを弾く仕組みを受注確定側にも用意する
(`distributor_catalog_ingestion_runs`と同じ考え方。[catalog-import-pipeline.md](catalog-import-pipeline.md)5章)。

## 5. 未確定: 「もう追加は来ない」をどう判定するか

複数回の確定を許すと、10個の発注に6個の確定が来た時点で、
**残り4個が「後日来る」のか「欠品で終わり」なのかをシステムは区別できない**。
確定1回の前提なら「CSVが届いた = それで確定、残りは欠品」と自動で決まっていた判定が、明示的に必要になる。

| 判定方法 | 使える条件 |
|---|---|
| 卸のCSVの完了フラグ・欠品列を見る | 卸がその列を出している場合。いちばん確実 |
| `Σ確定数量 = 発注数量`で完納とみなす | 数量が揃えば自動判定できる。揃わないまま止まった発注は宙に浮く |
| クリニック側が画面で締める | 上2つが使えない場合の最終手段。運用負荷が乗る |

上2つだけでは、数量が揃わないまま放置される発注が残る。**画面から締められる手段は別途必要になる見込み。**
なおこの判定は分納の有無と関係なく決めなければならない項目のため、4章の結論とは独立して詰める。
