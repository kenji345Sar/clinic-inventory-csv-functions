# CSVの文字コード(UTF-8 / Shift_JIS)の扱い

卸から届くCSVの文字コードをどう扱っているか、その前提となる仕組みをまとめる。
取り込み全体の設計は[catalog-import-pipeline.md](catalog-import-pipeline.md)、実装は
[csv_util.go](../internal/infrastructure/distributorcsvingestion/csv_util.go)の`decode`。

文字コードを他の形式差と分けて1本の文書にしているのは、**間違えても処理が止まらず、
化けたデータが最後まで通ってしまう**性質があるため。列がずれれば例外になるが、
文字コードの取り違えは成功したように見える。

最終更新: 2026-08-30

---

## 1. なぜ最初にUTF-8へ揃えるのか

Goの文字列も`encoding/csv`もUTF-8である前提で動く。Shift_JISのバイト列をそのまま
`csv.Reader`に渡すと、日本語が読めないだけでなく**列の区切り位置そのものがずれる**。
Shift_JISには2バイト目が`,`(0x2C)や`"`(0x22)と同じ値になる文字があり、
CSVの区切り文字と区別が付かないため。

そのため文字コードの変換は、パースより前・他のどの処理よりも先に1回だけ行う。

---

## 2. BOMとは何か、なぜ除去するのか

BOM（Byte Order Mark）はファイルの先頭に置かれる「この先の中身はこの文字コードです」という
目印。文字コード上は`U+FEFF`という1文字だが、**文章の一部ではなくしるし**である。

元はUTF-16のためのもので、2バイトを1組で読むUTF-16には「上位バイトが先か下位バイトが先か」
という並び順の問題があり、それを先頭で宣言する必要があった。UTF-8は1バイト単位なので
並び順の問題がなく**本来BOMは不要**だが、Windowsが「これはUTF-8です」という印として付ける
慣習を作り、Excelは今もCSVにこれを付ける。

```
BOM : EF BB BF   ← U+FEFF をUTF-8で表した3バイト
```

厄介なのは、受け取る側からは**ただの1文字にしか見えない**こと。除去せずに読むとこうなる。

```
BOM付きCSVの1列目 : "﻿コード"   見た目: ﻿コード
"コード" と等しいか: false
```

見た目は「コード」だが文字列としては一致しない。そのため卸商品コードの突合が
**エラーも例外も出さずに静かに失敗する**。原因に辿り着きにくい種類の不具合になる。

---

## 3. 文字コードは「判定」できない

前提として、**バイト列だけから100%確実に文字コードを判定する方法は無い**。
同じバイト列が両方の文字コードとして妥当に読めてしまう場合があり、
文字コードはファイルの中に書かれておらず外から与えられる情報だからである。

手段は4つあり、このプロジェクトは1番目を採っている。

| 手段 | 確実性 | 採否 |
|---|---|---|
| 卸との取り決め | 確実 | **採用**。卸別パーサに定数で宣言する |
| BOMの有無 | あればUTF-8と断定できる（無いUTF-8も普通にある） | 除去するだけで判定には使わない |
| UTF-8の規則違反を検査 | 日本語を含むなら実用上確実 | **申告との食い違いの検出に使う**（4章・5章） |
| 統計的な推定（nkf・chardet等） | 短いファイルでは外す | 使わない |

つまり**判定はせず、取り決めを信じたうえで、明らかに違う場合だけ検出して止める**。

---

## 4. UTF-8の規則違反で食い違いを見抜ける理由

UTF-8はバイトの並び方に厳格な規則があり、**先頭以外のバイトは必ず`10xxxxxx`(0x80〜0xBF)**
でなければならない。

| 文字 | ビットの形 |
|---|---|
| ASCII | `0xxxxxxx` |
| 2バイト文字 | `110xxxxx` `10xxxxxx` |
| 3バイト文字（日本語） | `1110xxxx` `10xxxxxx` `10xxxxxx` |

Shift_JISの日本語はこの規則をすぐ破る。「商品名」の3文字で比べるとこうなる。

```
UTF-8     : E5 95 86  E5 93 81  E5 90 8D   ← 1110xxxx 10xxxxxx 10xxxxxx を満たす
Shift_JIS : 8F A4  95 69  96 BC            ← 先頭が 8F = 10001111（継続バイトの形）
                                              → UTF-8として不正
```

逆に言えば、日本語を含むファイル全体がUTF-8の規則を満たしていれば、それはUTF-8とみなして
実用上問題ない。ただし**全部ASCIIのファイルには使えない**。どちらの文字コードでもASCII部分は
同じバイトになり、区別する材料が存在しないため、判定の対象外にする（`hasNonASCII`）。

---

## 5. デコーダは化けてもエラーにしない

ここが一番の落とし穴。`golang.org/x/text`のデコーダは**変換できない文字が来てもエラーを返さない**。
置換文字（U+FFFD、`�`）に差し替えて先へ進む。素通しすると取り込みは成功扱いになり、
商品名が化けたままDBに入る。

さらに、UTF-8のCSVをShift_JISとして読んだ場合は置換文字にすらならず、
**妥当な漢字に化ける**ことが多い。

```
CSVの中身（UTF-8）         : 商品名,単価
Shift_JISとして解釈した結果 : 蝠�刀蜷�,蜊倅ｾ｡
```

置換文字を探すだけでは後者を取りこぼすため、`decode`は検出を2段構えにしている。

| 宣言 | 検出条件 | そう判断してよい根拠 |
|---|---|---|
| UTF-8 | UTF-8として不正なバイトがある | 実際はShift_JIS等で送られてきた可能性が高い |
| Shift_JIS | 変換後に置換文字が出た | 変換できない文字が含まれていた |
| Shift_JIS | **中身がUTF-8として読める** | 4章のとおり、日本語のShift_JISが全体で妥当なUTF-8にもなることは実質ない |

検出したときは**行単位ではなくファイル単位で止める**。文字コードの食い違いはファイル全体に
及ぶため、1行だけ直しても意味がないから。`status`は`needs_review`になり、商品マスタは
1行も更新されない。
